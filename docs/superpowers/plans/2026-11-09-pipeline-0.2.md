# pipeline 0.2 Implementation Plan

> **For agentic workers:** implement task-by-task; each task is one worker, tests first, one or more commits, no push.

**Goal:** 0.2 of the `pipeline` plugin: the panel redesigned as an execution dashboard (Overview, Queue, History), a `session` runner that runs each item in its own headless Claude Code child with Stop and Log, and sibling sessions shown in the panel. The user's mockup is `docs/superpowers/specs/2026-11-09-pipeline-panel-redesign.html` (open it; its notes are the design brief).

**Spec:** `docs/superpowers/specs/2026-11-05-pipeline-design.md` (0.1) plus this plan.

## Global Constraints

- Everything of 0.1 holds (plugin folder, tool name, pure modules, no cross-plugin imports, tests with `claude plugin test plugins/pipeline`, `claude plugin validate`, tsc with the scratchpad tsconfig, the attribution trailers, no model identifiers in commits).
- Two workers run in parallel on one checkout. **File ownership**: Task A owns `hooks/pane.tsx`, `pane.test.tsx`, `draw.ts`, `status.ts`, `status.test.ts` and the `// ---------- panel ----------` section of `register.tsx` (the Pane and AbovePrompt `ui.render` hooks, `drawPane`, `barOf`, the `panel` atom and its `ui.input`/`ui.select`/button handlers). Task B owns new `hooks/runner.ts`, `runner.test.ts`, `hooks/live.ts`, `live.test.ts`, the tool's `start`/`stop`/`log` actions and `/pipeline` subcommand wiring in `register.tsx`, `config.ts` (`runner`, `limits.parallel`), the skills and README. Both may add to `types/index.d.ts` but only the types named below for them. Stage with explicit `git add` paths; never `-A`. Commit often; a restart loses uncommitted work.
- Shared contract, added to `types/index.d.ts` by Task B first thing (Task A codes against it and may stub it locally until B's commit lands):

```ts
export type ChildStatus = 'starting' | 'running' | 'stopped' | 'finished' | 'failed'
export type ChildSession = { id: string; item: string; worktree: string; branch: string; pid?: number; status: ChildStatus; startedAt: number; endedAt?: number; log: string; lastLine?: string }
export type Sibling = { sessionId: string; title: string; cwd: string; branch?: string; item?: string; seenAt: string; agents: AgentRun[]; signals: Signal[]; isStale: boolean }
export type View = 'overview' | 'queue' | 'history'
export type QueueFilter = 'inbox' | 'ready' | 'blocked' | 'parked' | 'all'
export type Panel = { view: View; filter: QueueFilter; search: string; expanded: string | null; isMoreShown: boolean; isCompact: boolean; isDoneCollapsed: boolean; autoOpenedFor: string }
```
  and `PluginState.pipeline` gains `children: ChildSession[]` and `siblings: Sibling[]`.

## Review Focus

1. Idle Overview with 28 inbox, 0 ready: hero says nothing runs and why, three metrics, three "needs specification" rows, two merged rows, no dotted grid, no empty cost tiles. (A)
2. Running Overview: hero with item id and title, progress bar accepted/total, the four steps with the current one marked, usage line, one agent card with role, model and effort, activity, elapsed; task timeline from the ledger; Up next. (A)
3. Queue: typing in the search narrows rows live; filter buttons switch groups with counts; a row expands to its note and `/pipeline status <id>`. (A)
4. `runner: session`: `/pipeline next` starts one child in the item's worktree, its row shows in Overview with Stop and Log; Stop kills it and marks the item blocked with the reason; the child's live entry and the ledger drive the task counter. (B)
5. A sibling desktop session on the same repo running `/pipeline next` appears in Overview as a session row with its item and agents, and vanishes when stale. (B, drawn by A)

### Task A: The dashboard panel

**Files:** `plugins/pipeline/hooks/pane.tsx`, `pane.test.tsx`, `draw.ts`, `status.ts`, `status.test.ts`, the panel section of `register.tsx`.

**Design (from the mockup; its CSS does not apply, its hierarchy does):**
- Header row: "Pipeline" and the project name with the branch; no tiles. Tabs as three Buttons: Overview, Queue (count), History. Footer line: agents running and open signals, or "No subagents running", plus `/pipeline status`.
- **Overview, idle**: hero (SVG on desktop: a state line `PIPELINE IDLE`, the headline `Nothing running right now`, one sentence: how many inbox, how many ready, what moves work: `/pipeline next` when something is ready, else "add specifications"), three metrics (Inbox, Ready, Merged this week) as compact SVG tiles, "Needs specification" or "Up next" list of three rows (id chip, title, size, status tag), "Recently merged" two rows with PR `#NN` links, each section with a "View queue →" / "View history →" Button that switches the tab. Sibling sessions, when any, as a section "Other sessions" (rows from `siblings`: title, item, agents count, stale dim).
- **Overview, running**: hero `BUILDING · P14` (pulsing dot), title, one line from the spec's What or the note, progress bar accepted/total with percent, steps Plan · Build · Review · Merge with done/current/pending marks from the item status and ledger (`planning` → Plan current; `building` → Build; final review dispatched or `review` → Review; `merged` → Merge). Usage line: elapsed, tokens, ≈cost. "Active agent" card(s): role from the dispatch (implementer/reviewer/final/escalate when the ledger says, else the agent name), model · effort, activity, a thin bar (elapsed over taskMinutes), calls · tokens, elapsed. "Task progress" timeline from the ledger tasks (accepted ✓, current ●, pending ○, blocked ✕) with the dispatch's model and elapsed on the current one. "Up next": the next ready item or first inbox. Child sessions (`children`) when the runner is `session`: one card per child with item, task counter from its ledger, status, Stop and Log Buttons (handlers call the tool actions `stop { item }` and `log { item }` that Task B provides; until then call them and show the answer text in a toast).
- **Queue**: an `Input` (key `pipeline-search`, placeholder "Find an item by name or id…"), filter Buttons Inbox · N, Ready · N, Blocked · N, Parked · N, All; a counter line; rows (id chip, title, size · status · readiness reason when inbox), a status tag; clicking a row expands it under: the note, needs, spec path, and `/pipeline status <id>`; empty state text. Search and filter live in the `panel` atom through `ui.input` and button handlers.
- **History**: a hero with merged-this-week count, then "Recent pull requests" rows (id chip in green, title, ✓ Merged, PR link) for every merged item newest first, folded past 20.
- Terminal and other surfaces keep `renderText` (the text block), extended with the view's name only.
- Remove the dotted grid and the large agent cards from `draw.ts`; keep the SVG helpers that still draw (hero, metric tile, progress bar, agent bar, pulsing dot). Colours: purple running `#a59aff`, green merged `#72d1a6`, amber blocked/no spec `#f1bd7e`, muted `#7f828f`, as the mockup.

### Task B: The session runner and sibling sessions

**Files:** `plugins/pipeline/hooks/runner.ts`, `runner.test.ts`, `live.ts`, `live.test.ts`, `config.ts`, `config.test.ts`, `types/index.d.ts` (the contract above), the tool and command sections of `register.tsx`, `skills/pipeline-run/SKILL.md`, `skills/pipeline-rules/SKILL.md`, `README.md`, `.claude-plugin/plugin.json` (version 0.2.0 in the last commit).

**Design:**
- Config: `runner: 'subagent' | 'session'` (default `subagent`), `limits.parallel` (default 1; with `session`, `run all` starts up to this many items whose `needs` are merged and that no other item in flight names).
- `runner.ts` (pure where possible): `childArgv({ item, worktree, prompt, permissionMode })` → `['claude', '-p', prompt, '--permission-mode', mode, '--output-format', 'text']` plus whatever flag the installed CLI needs to load plugins the same way the parent does (check `claude --help`; the parent's plugin set is the user's, so a child started from the same machine loads them); `childPrompt(item)` → "Run item pN with the pipeline-run skill, runner subagent, from pick to merge; the worktree is this directory"; `parseChildLine`; the child record lifecycle.
- Tool actions: `start { item }`: refuses unless `config.runner === 'session'`, the item is `ready` or `blocked`-resumable, the session's permission mode (`$.session.permissionMode()` or the nearest API; grep the ref types) is `acceptEdits`, `auto`, `dontAsk` or `bypassPermissions` (else answer what to switch to), and `children` running < `limits.parallel`; creates the worktree (`git worktree add .claude/worktrees/<id> -b feat/<id> <mainBranch>` via `$.process.run`, reusing an existing one), spawns the child with `$.process.spawn` in that cwd, streams its output to `<git common dir>/pipeline/<id>.log` (append through `$.fs.write` of the whole buffer is acceptable if no append exists), keeps `ChildSession` in the `children` atom, marks the item `building` with note `session runner`, answers one line. `stop { item }`: ends the stream loop (kills the child), marks the item `blocked` with `stopped by the user` unless it had finished, answers. `log { item }`: the last 60 lines of the log. A child that exits 0 leaves the item as the child left it; non-zero → `blocked` with the exit code and the log tail in the note.
- Live file: a child session writes its own entry (it is a normal session with the plugin loaded), keyed by its session id, with `item` set from the `update … building` it makes. `live.ts` gains `siblingsOf(live, selfId, now)` → `Sibling[]` (every other entry, `isStale` past 3 minutes) and the mod keeps the `siblings` atom current on each tick and heartbeat. `deadAgents` is unchanged.
- `/pipeline next` and `run` with `runner: session` hand the model a prompt that calls `start` instead of running in-session (the run skill's step 2 says: with runner session, call `start` and answer the one line; the child does the rest). `/pipeline stop <id>` and `/pipeline log <id>` added. `run all` starts up to `limits.parallel` children and, on each child's exit, the lead (woken by the `ScheduleWakeup` the mod already schedules) starts the next ready item: say so in the run skill.
- Watchdog for children: a child's agents are watched by the child's own plugin; the parent's `tick` flags a child whose live entry is stale while its process runs as `silent`, and a child process that died with the item still `building` as `dead` (then Stop conditions apply via the skill).
- README: a "Runners" section (the trade-off: a child cannot ask you; permission modes; parallel items), the Stop and Log buttons, sibling sessions.

**Steps:**
- [ ] Types contract first, commit `pipeline: 0.2 state types`.
- [ ] Tests: `runner.test.ts` (argv, prompt, lifecycle), `config.test.ts` (runner, parallel), `live.test.ts` (siblings, stale), tool tests for `start` refusals (runner subagent, wrong permission mode, parallel limit, not ready), `start` spawning a fake process via a `process.spawn` hook mock, `stop`, `log`, non-zero exit → blocked. Review Focus 4 and 5.
- [ ] Implement; skills and README; version 0.2.0. Commits per piece.
