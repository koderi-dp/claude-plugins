# pipeline-migrate

One command, run once, in the main checkout on a clean `mainBranch`. The tool does the reading and the writes; you do the judgment: what each piece of the old process becomes (a config key, a `rules.md` line, a backlog item, the active item, or history). Nothing is written before step 5.

## Steps

1. **Read.** `{ "action": "migrate" }` answers `{ sources, config, sourcesOfConfig, items, rules, active, bulk, unsure, report }` and writes nothing; it is refused when `docs/pipeline/config.json` exists unless `refresh: true`. `sources` is every file it read, in the spec's order (CLAUDE.md and `*/CLAUDE.md`, docs/WORKFLOW.md, docs/backlog.md, docs/SLICES.md, the files CLAUDE.md links as a queue, status, workflow or ledger, specs and plans, ledgers, project skills, the Makefile, package scripts and the CI workflows). `items` is one `Partial<Item>` per queue entry in the queue's order (a checked item links the spec and the plan its bullet names); `rules` is a list of `{ group, line, source }`; `active` is a `building` item per open `feat/*` branch that has a ledger (branches are read from `.git/refs/heads` and `packed-refs`), with its `resume` block read from the ledger's current status; `bulk` is `{ files, count }`, the files under `.superpowers/sdd/<increment>/` of merged increments except `progress.md` and the final review, where an increment counts as merged only when its plan path is a merged item's plan; `unsure` names the increments whose folder is merely named like a merged item, for you to decide; `report` lists each file and what was taken from it.
2. **Finish the mapping.** Read what the tool could not classify yourself: the sections of CLAUDE.md and WORKFLOW.md about how work is run, project skills about dispatch or review, and every `rules` line (they are candidates found by sentence patterns, not decisions). Move a line to the right group, drop one the config already enforces, and shorten each to one sentence. Check the items: a deferral that lives only in an old item's prose becomes its own `inbox` item with the source quoted; a status git proves wrong is corrected (a checked item whose PR is not on `mainBranch` stays `inbox` with its note); the openhuddle-style `needs` name queue labels, so map them to the ids the items will get. Link existing specs and plans from the items they belong to; move or rewrite nothing. A `riskyPaths` entry whose source says "broad" (a whole top-level directory or `src` tree, which would send most diffs to an independent review) is narrowed to the auth, migration, payment or parser folders the prose meant, or dropped. A rule that contradicts another is a question for step 4.
3. **Show.** In one message: the status block the backlog would give (counts per status, the active item with its resume line, how many items are unverified), the config with the source of every key, the rules by group with their sources, and the sections of CLAUDE.md and WORKFLOW.md that will be replaced by the pointer paragraph. The queue's open decisions are not items: the tool turns each into a `before dispatch` rule (`Stop before <the decision>: open user decision since <date>.`), shown with the other rules.
4. **Ask once.** One sentence asking for corrections. The user answers in a sentence or two ("p3 is done, p7 before p5, merge stays manual"); apply it to the drafts. This is the one interaction.
5. **Apply.** `{ "action": "migrate-apply", "config": <config>, "items": <items>, "rules": <rules> }`, where `items` is the corrected list plus the `active` items, in the order the backlog should have. It normalizes the config (refused with the problems when a key is wrong), adds the items in order with new `p<n>` ids, maps a queue label in `needs` (`Q7`) to the id that entry got (an unknown label goes into the note), writes a `building` item's `resume` into `docs/pipeline/ledgers/<id>.json` with the old ledger path as `importedFrom`, writes a spec stub `docs/pipeline/specs/<id>.md` (the five headings of `templates/spec.md`, What from the note, Why from the source, one acceptance line) for every `inbox` or `building` item without a `spec`, so the needs-free ones settle to `ready`, writes `config.json`, `rules.md`, `backlog.json` and `BACKLOG.md`, and prepends `Historical. The queue is docs/pipeline/backlog.json since <date>.` once to `docs/backlog.md`, `docs/SLICES.md`, `.superpowers/sdd/progress.md` and `progress-archive.md`, and every nested `progress.md` and `final-review*.md` under `.superpowers/sdd/`. It answers the status text, `spec stubs written for N items`, `historical line added to N files` and the bulk files again, one per line: remove those with `git rm` once the user has confirmed in step 4 (the tool deletes nothing; `retain.superpowers: true` keeps them). Its last line, `commit docs/pipeline/ on <mainBranch> now: git add docs/pipeline && git commit`, is done in step 7: every file under `docs/pipeline/` is versioned and never gitignored. It refuses when `docs/pipeline/` already exists unless `refresh: true`; a refresh leaves `config.json` as it is (written only when missing), keeps `rules.md` when it exists, matches items by id or title and refreshes only their titles, sources and links (`spec`, `plan`, `pr`, `ledger`), adds items that are new, and changes no status.
6. **Retire the prose.** Rewrite the sections of CLAUDE.md about how work is run (the loop, roles and models, dispatch, approval gates, ledgers, resume, standing instructions on process) into one paragraph: the project runs on the pipeline plugin, the config is `docs/pipeline/config.json`, start with `/pipeline status`. Keep code conventions, layout, commands, decisions already made and the definition of done. `docs/WORKFLOW.md` becomes the same pointer paragraph with its "what the slices taught" section kept. Delete project skills that only restated dispatch rules; skills that do something else stay, and `config.afterMerge` names them.
7. **Commit.** On a branch `chore/pipeline-migration`: the new files (all of `docs/pipeline/`: `config.json`, `rules.md`, `backlog.json`, `BACKLOG.md`, the specs and the ledgers), the Historical lines, the rewritten prose and the deleted skills, with the attribution lines this session was given and no model identifier. Open the PR with the migration report (the files read and what was taken from each) and merge it under the project's own rule (`config.merge`).
8. **Check.** `/pipeline status` in a fresh session must show the picture the old docs gave, and the first item's briefs must carry the rules the old prose carried. What git cannot prove stays `inbox` with its note, and the status block says how many are unverified.

## From a file backlog to issues

When the project already has `docs/pipeline/backlog.json` and the user asks for GitHub issues as the queue, the steps above do not apply; these do. Run it in the main checkout on a clean `mainBranch`, with `gh` logged in.

1. **Draft.** `{ "action": "migrate-github" }` answers `{ create, active, skipped, remove }` and writes nothing: `create` is every item that becomes an issue, in backlog order, with its spec file when it has one; `active` names the items in flight: those in `planning`, `building` or `review`, which will carry the `pipeline:building` label, and the `blocked` ones, which will carry `pipeline:blocked`; `questions` names the `inbox` items whose spec still has an open question, which will be asked on the issue; `skipped` counts the merged items, which get no issue because their PRs are the record, and lists the parked ones, which the user files by hand when wanted; `remove` is the files the project no longer needs.
2. **Show and ask once.** In one message: the items that become issues, the ones in flight, the parked ones and the files to remove. Then one sentence asking for corrections and whether to proceed. A correction to an item (a title, a status) is made with `update` on the file backlog before the apply; nothing else is changed by hand.
3. **Apply.** `{ "action": "migrate-github", "apply": true }`. It creates a labelled issue per item with the title, the spec's What and Why as the body (the note when there is no spec), then the id the item had (`Migrated from p78.`) and a `Needs: #<n>` line naming the issues of the items it waited for, posts the spec as the spec comment with the item's state in its status line (the PR for an item in review, the note for another item in flight), labels and assigns an item in `planning`, `building` or `review`, labels a `blocked` one `pipeline:blocked`, asks an open question as a question comment with `pipeline:needs-info`, copies each in-flight item's ledger to `.git/pipeline/<issue>/ledger.json` (a fresh one with its branch when it had none) and its plan and briefs to `<worktree>/.pipeline/<issue>/`, copies `facts.md` to `.git/pipeline/facts.md`, sets `queue: github` in the config and adds `.pipeline/` to `.git/info/exclude`. It answers one `<old id> → #<issue>` line per item, the parked ids and the paths to remove. It deletes nothing. When it stops on a GitHub error, the issues already made stay and the answer lists them; run the apply again and it skips every item whose title already has a labelled open issue, and posts no comment that issue already has.
4. **Remove and commit.** `git rm -r --ignore-unmatch` the listed paths, then commit the removal together with `docs/pipeline/config.json`, with the attribution lines this session was given and no model identifier. An item in flight resumes from its ledger with `/pipeline run <issue>` on this machine.

## Reply shape

Steps 1 and 2 answer nothing; step 3 is the one long message; from step 5 on, one line per step: `migrated · 16 items (10 inbox, 6 merged, 10 unverified) · 9 rules · PR #31`.
