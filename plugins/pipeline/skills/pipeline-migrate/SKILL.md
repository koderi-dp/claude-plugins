# pipeline-migrate

One command, run once, in the main checkout on a clean `mainBranch`. The tool does the reading and the writes; you do the judgment: what each piece of the old process becomes (a config key, a `rules.md` line, a backlog item, the active item, or history). Nothing is written before step 5.

## Steps

1. **Read.** `{ "action": "migrate" }` answers `{ sources, config, sourcesOfConfig, items, rules, active, bulk, unsure, report }` and writes nothing; it is refused when `docs/pipeline/config.json` exists unless `refresh: true`. `sources` is every file it read, in the spec's order (CLAUDE.md and `*/CLAUDE.md`, docs/WORKFLOW.md, docs/backlog.md, docs/SLICES.md, the files CLAUDE.md links as a queue, status, workflow or ledger, specs and plans, ledgers, project skills, the Makefile, package scripts and the CI workflows). `items` is one `Partial<Item>` per queue entry in the queue's order (a checked item links the spec and the plan its bullet names); `rules` is a list of `{ group, line, source }`; `active` is a `building` item per open `feat/*` branch that has a ledger (branches are read from `.git/refs/heads` and `packed-refs`), with its `resume` block read from the ledger's current status; `bulk` is `{ files, count }`, the files under `.superpowers/sdd/<increment>/` of merged increments except `progress.md` and the final review, where an increment counts as merged only when its plan path is a merged item's plan; `unsure` names the increments whose folder is merely named like a merged item, for you to decide; `report` lists each file and what was taken from it.
2. **Finish the mapping.** Read what the tool could not classify yourself: the sections of CLAUDE.md and WORKFLOW.md about how work is run, project skills about dispatch or review, and every `rules` line (they are candidates found by sentence patterns, not decisions). Move a line to the right group, drop one the config already enforces, and shorten each to one sentence. Check the items: a deferral that lives only in an old item's prose becomes its own `inbox` item with the source quoted; a status git proves wrong is corrected (a checked item whose PR is not on `mainBranch` stays `inbox` with its note); the openhuddle-style `needs` name queue labels, so map them to the ids the items will get. Link existing specs and plans from the items they belong to; move or rewrite nothing. A rule that contradicts another is a question for step 4.
3. **Show.** In one message: the status block the backlog would give (counts per status, the active item with its resume line, how many items are unverified), the config with the source of every key, the rules by group with their sources, and the sections of CLAUDE.md and WORKFLOW.md that will be replaced by the pointer paragraph.
4. **Ask once.** One sentence asking for corrections. The user answers in a sentence or two ("p3 is done, p7 before p5, merge stays manual"); apply it to the drafts. This is the one interaction.
5. **Apply.** `{ "action": "migrate-apply", "config": <config>, "items": <items>, "rules": <rules> }`, where `items` is the corrected list plus the `active` items, in the order the backlog should have. It normalizes the config (refused with the problems when a key is wrong), adds the items in order with new `p<n>` ids, maps a queue label in `needs` (`Q7`) to the id that entry got (an unknown label goes into the note), writes a `building` item's `resume` into `docs/pipeline/ledgers/<id>.json` with the old ledger path as `importedFrom`, writes `config.json`, `rules.md`, `backlog.json` and `BACKLOG.md`, and prepends `Historical. The queue is docs/pipeline/backlog.json since <date>.` once to `docs/backlog.md`, `docs/SLICES.md` and every `progress.md` and `final-review*.md` under `.superpowers/sdd/`. It answers the status text, `historical line added to N files` and the bulk files again, one per line: remove those with `git rm` once the user has confirmed in step 4 (the tool deletes nothing; `retain.superpowers: true` keeps them). It refuses when `docs/pipeline/` already exists unless `refresh: true`; a refresh merges the config over the file, keeps `rules.md` when it exists, matches items by id or title and refreshes only their titles, sources and links (`spec`, `plan`, `pr`, `ledger`), adds items that are new, and changes no status.
6. **Retire the prose.** Rewrite the sections of CLAUDE.md about how work is run (the loop, roles and models, dispatch, approval gates, ledgers, resume, standing instructions on process) into one paragraph: the project runs on the pipeline plugin, the config is `docs/pipeline/config.json`, start with `/pipeline status`. Keep code conventions, layout, commands, decisions already made and the definition of done. `docs/WORKFLOW.md` becomes the same pointer paragraph with its "what the slices taught" section kept. Delete project skills that only restated dispatch rules; skills that do something else stay, and `config.afterMerge` names them.
7. **Commit.** On a branch `chore/pipeline-migration`: the new files, the Historical lines, the rewritten prose and the deleted skills, with the attribution lines this session was given and no model identifier. Open the PR with the migration report (the files read and what was taken from each) and merge it under the project's own rule (`config.merge`).
8. **Check.** `/pipeline status` in a fresh session must show the picture the old docs gave, and the first item's briefs must carry the rules the old prose carried. What git cannot prove stays `inbox` with its note, and the status block says how many are unverified.

## Reply shape

Steps 1 and 2 answer nothing; step 3 is the one long message; from step 5 on, one line per step: `migrated · 16 items (10 inbox, 6 merged, 10 unverified) · 9 rules · PR #31`.
