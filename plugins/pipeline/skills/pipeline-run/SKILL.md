# pipeline-run

One item at a time, from `ready` to `merged`, with the lead (you) dispatching subagents and recording every boundary through `mcp__pipeline__pipeline`. With `config.runner` = `session` the lead only starts child sessions and each child is the lead of its own item (see Runner session below). The templates in this plugin's `templates/` folder (`implementer.md`, `reviewer.md`, `fix.md`, `final.md`) are the briefs; each names its `{{placeholders}}` in its first line. Fill every placeholder, save the filled brief to `docs/pipeline/ledgers/<id>/task-N-brief.md` (a fix round: `task-N-fix-R-brief.md`, a reviewer: `task-N-review-brief.md`) and the report to `task-N-report.md`, and never put a backlog or ledger instruction in a brief. **Two homes for the pipeline's files.** What you write by hand (the plan, the briefs, the reports, a spec written at pick) goes into the worktree you are in, at the relative path, and is committed on the item's branch: it reaches `mainBranch` through the PR. Once you have entered the worktree the engine refuses an edit at the main checkout's path, so never write `<root>/docs/pipeline/...` by hand. What the tool writes (`backlog.json`, `BACKLOG.md`, `ledgers/<id>.json`) lives in the main checkout whatever your cwd, and is committed on `mainBranch` at Close. `{{attribution}}` is the attribution lines this session was given; no model identifier goes into commits, PR text or comments.

Every reply during a run is one line: `p12 · task 3/6 · implementer sonnet 14 min · fix round 1`. A milestone adds what changed. Nothing else: no summaries, no offers.

## Steps

1. **Read.** `{ "action": "get" }` answers the config, the backlog, the active item's `resume` block and open watchdog signals. Act on a signal first (see Watchdog signals). Read `docs/pipeline/rules.md`: each group goes into the brief or step it names (`before dispatch` → your checklist before each Agent call; `in every implementer brief` → `{{rules}}` of implementer.md and fix.md; `in every reviewer brief` → reviewer.md; `before the PR` → final.md and step 9; `after merge` → step 11).
2. **Pick.** The first `ready` item in array order, or the named id. A named item, or the first `inbox` item when nothing is `ready`, that has a `note` but no `spec` does not stop: write the spec from the note with the intake template (`templates/spec.md`, the five headings, Open empty when the note raises no question), `{ "action": "update", "id": "p12", "set": { "spec": "docs/pipeline/specs/p12.md" } }`, and continue (the tool settles it to `ready` when its `needs` are merged). Otherwise an item that is not `ready` stops with the reason, an open question in its spec or a `needs` id not merged, except a `blocked` item named by id, which resumes (see Out of `blocked` under Stop conditions). **Runner session** (`config.runner` is `session`, the parent): stop here and call `{ "action": "start", "item": "p12" }` instead; answer its one line and nothing else (see Runner session). **In a child session** (the prompt that started you says the session runner set the item building and that the worktree is this directory): skip this status change and the worktree step, make the ledger call below and continue with step 3; on a resume, go to Resume. Otherwise: `{ "action": "update", "id": "p12", "set": { "status": "planning" } }`; `EnterWorktree` named `p12`, branch from `config.branch` (`feat/p12`) off `mainBranch`; `{ "action": "ledger", "item": "p12", "set": { "branch": "feat/p12", "worktree": ".claude/worktrees/p12", "base": "<merge base sha>", "plan": "docs/pipeline/plans/p12.md" } }`. Notify when `notify` is not `off`: item started.
3. **Plan.** `superpowers:writing-plans` from `docs/pipeline/specs/p12.md` into `docs/pipeline/plans/p12.md` (committed on the branch). Tasks are `### Task N:` headings, each with the files it owns, pinned names, its check command and a review focus. Pre-flight scan: for every name one task produces and another consumes, check that both sides agree on file, signature and shape; each conflict you settle becomes a ruling: `{ "action": "ledger", "item": "p12", "set": { "rulings": [{ "task": 2, "text": "...", "why": "...", "costIfWrong": "..." }] } }`. No pause for plan review. Then `update` to `building` and `{ "action": "ledger", "item": "p12", "set": { "tasks": [{ "n": 1, "title": "...", "status": "pending", "dispatches": [] }, ...], "resume": { "task": 1, "state": "planned", "lastVerified": "<base sha>" } } }`.
4. **Dispatch a task**, with `superpowers:subagent-driven-development` as the loop and this plugin's templates as the briefs. Fill `implementer.md` (task verbatim, owned and forbidden files, pinned names, carried minor findings, `checks.fast`, `checks.task`, the rules group, attribution). Call the Agent tool with `model` and `effort` from `config.models.implementer` and the brief as the prompt. Before the call: `ledger` with the task `status: "running"` and `resume: { "task": N, "state": "implementer dispatched", "lastVerified": "<last accepted sha>" }`.
5. **Read the result**: the report, `git diff <lastVerified>..HEAD` and the test files, yourself. Record the dispatch: `{ "action": "ledger", "item": "p12", "set": { "tasks": [{ "n": 2, "dispatches": [{ "role": "implementer", "model": "sonnet", "effort": "medium", "brief": "docs/pipeline/ledgers/p12/task-2-brief.md", "tokens": 240000, "minutes": 31, "result": "fix round 1" }] }] } }` (tokens and minutes from the Agent result; `brief` is the brief's path, and the tool keeps fields it does not know). A defect, a missing test, a claim the diff does not support: fix round.
6. **Fix round**: fill `fix.md` with the findings verbatim, `{{round}}` of `{{max}}` = `limits.fixRounds`, saved to `docs/pipeline/ledgers/p12/task-N-fix-R-brief.md` and named in the dispatch entry's `brief`, to the same implementer (same model and effort, the Agent resumed where the host allows it, a fresh one with the brief otherwise); task `status: "fix"`, `resume.state: "fix round N dispatched"`. Past `limits.fixRounds`: one re-dispatch at `config.models.escalate` with every failure in the brief, recorded as a dispatch with `role: "escalate"`; still failing → Stop conditions.
7. **Independent review** only when the task's diff touches `config.riskyPaths`: `git diff --name-only <lastVerified>..HEAD` matched against each glob (`**` crosses directories; a match on any file is enough). Fill `reviewer.md` (brief and report paths, commit range, the matched paths, the plan's review focus, `checks.task`, the reviewer rules), saved to `task-N-review-brief.md`, Agent with `config.models.reviewer`, record the dispatch with `brief` and with `risky` naming the first matched path. `FIX REQUIRED` → step 6 with the findings verbatim, then a scoped re-review of the fix commit by the same reviewer brief with the findings as focus. Minor findings are not fixed now: they are `{{carried}}` in the next brief. No risky path: your reading in step 5 is the review (`kind: "lead-diff"`).
8. **Accept**: `{ "action": "ledger", "item": "p12", "set": { "tasks": [{ "n": 2, "status": "accepted", "commits": "c1d2e3f..9e8d7c6", "review": { "kind": "independent", "verdict": "approved after fix round 1", "carried": ["minor: log line wording"] } }], "resume": { "task": 3, "state": "task 2 accepted", "lastVerified": "9e8d7c6" } } }`, then `git push -u origin feat/p12`, so a lost working tree never loses an accepted task. `notify: all` → one line. Next task from step 4; after the last, step 9.
9. **Final review.** Fill `final.md` (merge base and head, the spec's Acceptance list verbatim, the ledger's rulings, what the plan parked, `checks.gate`, the `before the PR` rules), Agent with `config.models.final`, `resume.state: "final review dispatched"`. `FIX REQUIRED` → one fix wave (one `fix.md` per task touched, to that task's implementer), then one scoped re-review. A `MISSING` acceptance line after that wave is a stop. Then run `checks.gate` yourself in the worktree; red is not done: one fix wave, then Stop conditions. Record: `{ "action": "ledger", "item": "p12", "set": { "final": { "verdict": "approved", "gate": "green", "tokens": 180000 } } }`.
10. **PR.** `git push -u origin feat/p12`; open the PR against `mainBranch` with: the item title; the Acceptance list ticked line by line; the rulings; what was parked; the token total from the ledger; the attribution footer the session was given. `{ "action": "ledger", "item": "p12", "set": { "pr": "#31" } }` and `update` with `"pr": "#31"`. `subscribe_pr_activity` on it. `merge: pr` → `update` to `review`, notify (PR open), go to step 11's summary with `review` instead of `merged` and take the next item under `run all`. `merge: auto` → wait for CI through the subscription; green with no open Critical or Important → merge with `config.mergeMethod` (`merge` commit by default, or `squash`); red → one fix wave through step 6 and one push; red again → Stop conditions.
11. **Close.** First, from the main checkout, not the worktree: `git -C <root> checkout mainBranch && git pull`, so the pull never meets a changed `backlog.json`. Then `{ "action": "update", "id": "p12", "set": { "status": "merged", "pr": "#31" } }` (the tool regenerates `BACKLOG.md`). Clean: `{ "action": "clean", "item": "p12" }` lists what `config.retain` says may go (the item's briefs, reports and logs under `docs/pipeline/ledgers/p12/`, the plan when `retain.plans` is off, whatever superpowers' skills wrote for it under `.superpowers/sdd/`); remove every listed path with `git rm -r -q` (plain `rm -r` for untracked ones). The spec and `ledgers/p12.json` always stay. Then commit `docs/pipeline/backlog.json`, `docs/pipeline/BACKLOG.md`, `docs/pipeline/ledgers/p12.json` and the removals on `mainBranch` and push. `ExitWorktree` (remove it). Run each `config.afterMerge` entry: a path is regenerated or checked, a command is run, a skill name is invoked. The `after merge` rules apply here. Notify (merged). Reply: `p12 merged · PR #31 · 6 tasks · 2 rulings · 1.4M tokens · next: p13`. Under `run all`, back to step 1; no ready item left → the status line and stop.

## Runner session

`config.runner` = `session` runs each item in a headless Claude Code child of its own (`claude -p` in the item's worktree, the installed plugins loaded, this session's permission mode) instead of in this session. The child cannot ask anyone anything: it runs only when this session's mode is `acceptEdits`, `auto`, `dontAsk` or `bypassPermissions`, and `start` refuses otherwise, naming the modes.

- **The parent** (`/pipeline next`, `/pipeline run <id>`): `{ "action": "get" }`, then `{ "action": "start", "item": "p12" }` for the first ready item or the named one (a `blocked` item resumes), and answer the tool's one line (`started p12 in .claude/worktrees/p12 · session <id> · log .git/pipeline/p12.log`). The tool makes the worktree, sets the item `building` with the note `session runner`, records `branch` and `worktree` in the ledger and spawns the child; the child's one-line replies and tool uses stream into the log. Never plan, dispatch or merge in the parent while a child runs the item.
- **`run all`**: `start` up to `limits.parallel` items whose `needs` are merged (the tool refuses the one past the limit; the refusal is the signal to wait). Each `get` answers `children` with each child's `status`; when one is `finished` or `failed` and a slot is free, `start` the next ready item. Between starts the mod schedules a wake-up every `limits.silentMinutes` while a child runs, so you are brought back without a user turn; on the wake-up, `get` and continue. A `failed` child left its item `blocked` with the exit code and the log tail in the note.
- **The child** runs this skill from step 2's ledger call to step 11 in its own session, with `runner subagent` (a child never starts children). Its `/pipeline`-free prompt already names the item; its first tool call is `get`. The parent's panel shows the task counter from the ledger the child writes, with Stop and Log.
- **`stop { item }`** (`/pipeline stop p12`, the panel's Stop) kills the child and sets the item `blocked` with `stopped by the user`; `log { item }` (`/pipeline log p12`, the panel's Log) answers the last 60 lines. A stopped or failed item is started again with `/pipeline run p12`: the worktree and branch are reused and the child resumes from the ledger.
- Signals for a child in a `get` answer name the agent `child p12`: **silent** (its live entry has had no heartbeat for three minutes while its process runs) → read `log`; a child that is working shows tool uses there; one that is stuck → `stop`, then `run p12`. **dead** (its process exited with the item still `building`) → `run p12` resumes it.

## Stop conditions

Before any of these: `{ "action": "update", "id": "p12", "set": { "status": "blocked", "note": "<reason>" } }`, `{ "action": "ledger", "item": "p12", "set": { "blockers": ["<reason>"] } }`, notify, and either wait for the user (`next`, `run <id>`) or take the next ready item (`run all`). The worktree stays for the resume.

Out of `blocked`: `/pipeline run <id>` on a blocked item resumes it. Read the item's `note` and the user's answer in the conversation; `update` to `building` (`ready` when nothing was built yet) with a `note` recording the resolution in a few words (the ledger's `blockers` list is history and stays); then Resume.

- Any entry of `config.stop` applies to what the task needs (read them as text; the defaults are a product decision the spec leaves open, a security trade-off, CI that cannot be made green, credentials or external services, new cost, a destructive data change).
- An implementer escalated once still fails (step 6).
- CI or `checks.gate` is red after one fix wave (steps 9 and 10).
- The ledger's `tokens` reaches `limits.itemTokens`, or a task passes `limits.taskMinutes`: finish the running task, then block.
- The spec's Open heading is not empty, found at pick or during the build.
- A protected path (`config.protectedPaths`) must change and the spec does not say so.

## Resume

1. `{ "action": "get" }`: the active item (`planning`, `building` or `review`) and its `resume` block. An item in `planning` with no resume block restarts at Pick's step 2 and step 3, reusing the worktree and branch when they exist (never a second one). No active item: say the status line and wait.
2. Enter the worktree before any dispatch: `EnterWorktree` with the ledger's `worktree` path. When the folder is gone, fetch the branch (`git fetch origin <ledger.branch>`, pushed at every accept) and recreate it: `git worktree add <path> <branch>`. In a child session you are already in the worktree: skip this step's `EnterWorktree` and recreation (never run `EnterWorktree`, never create another worktree) and go on with the checks. Then check the branch is checked out there and `resume.lastVerified` is on it. The working tree: `git status --porcelain` and `git log lastVerified..HEAD`. A commit after `lastVerified` is the implementer's claim, not verification, and a WIP commit is not verification either: re-run `checks.task` yourself, and treat the result as step 5 of that task. Uncommitted changes from a dead agent: keep them, they are the surviving tree the re-dispatch starts from.
3. Continue at `resume.task` in the state named (`implementer dispatched` → re-dispatch with the same brief from `ledgers/p12/task-N-brief.md` and a line saying what already exists in the tree; `fix round N dispatched` → the same with the fix brief from `task-N-fix-R-brief.md`, or, when that file is missing, re-read the diff as step 5 and write a new one; `final review dispatched` → step 9; `pr open` → step 10's wait). Say so in one line: `p12 · resumed at task 3/6 · fix round 2 · tree verified at b70de44`.

## Watchdog signals

Every `get` answer may carry open signals from the mod; each is delivered once, so act in the turn you read it and name it in the line.

- **silent** (no step for `limits.silentMinutes`): once, send the agent a request for a report; no answer by the next `get` → stop it (`TaskStop`), record the dispatch as `result: "stopped: silent"`, re-dispatch from the surviving tree.
- **dead** (the session restarted with agents running): the signal names them; go to Resume and re-dispatch from the surviving working tree, never from `lastVerified` alone.
- **looping** (the same failing command three times, or fix rounds over `limits.fixRounds`): stop the agent, re-dispatch once at `config.models.escalate` with the failures in the brief, recorded as a dispatch with `role: "escalate"`; a second failure → Stop conditions.
- **budget** (`limits.taskMinutes` or `limits.itemTokens`): finish the running task, then Stop conditions.

Between items under `run all`, schedule a wake-up every `limits.silentMinutes` (`send_later` or the host's equivalent) so a silent agent is noticed without a user turn; the mod schedules one itself while a subagent or a child session runs, where the host offers `ScheduleWakeup`.
